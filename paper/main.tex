\begin{abstract}
LLM agents are meant to obtain ground truth from tool results, but tools can fail silently: a Model Context Protocol (MCP) server returns a well-formed success whose content is wrong, for example after its upstream API changes behaviour without changing its schema.
Published studies show that such failures occur and that agents often adopt the wrong values; a schema checks shape, not meaning, and a specification diff of an unchanged document reports nothing. Runtime monitors can warn the current agent, but the tool stays broken for every later one.
We present \fiks, a loop that turns a silent tool failure into a reviewable fix.
A proxy checks every successful MCP result against an outcome contract, including agreement with the raw upstream HTTP exchange and read-after-write, and returns a receipt to the agent.
A violation is compiled into a deterministic reproduction test that must fail on the current code for the named property; a tool-restricted coding agent repairs the server; and a pull request is opened only after that test, the full contract suite, all stored traces, typecheck, lint and CI on the exact commit pass. \fiks{} never merges.
In a pilot with \nDrifts{} seeded drifts on a mock vendor whose OpenAPI document does not change, \fiks{} flagged all \nDetected, produced a valid fail-first test for each, and obtained a green-CI pull request in one repair attempt per drift (\minsMin--\minsMax{} minutes from violation to PR; \$\costMin--\$\costMax{} per repair at API prices).
In a \nTasks-task, \kTrials-trial agent bench, pass$^5$ was \pFiveBd{} without \fiks, \pFiveB{} with receipts and \pFiveC{} after the fixes were merged; the pilot is too small to establish the receipt effect (sign test $p=\pairP$), and an earlier receipt wording did worse than no monitor (also not significant).
We position \fiks{} against a catalog of 508 sources, state which of its parts are not new, and release a pre-registration draft for a confirmatory study that has not yet been run.
\end{abstract}

\section{Introduction}
\label{sec:intro}

When a tool fails loudly, with an exception or an error result, the agent can retry, an error tracker can file an issue, and a coding agent can be pointed at the stack trace~\cite{sentry-seer-issue-fix,devin-oncall}.
When a tool fails silently, none of this happens: a Model Context Protocol (MCP) server returns a well-formed success whose content is wrong.
One cause, and the one this paper targets, is upstream drift: the vendor API behind the server changes a unit, a field name, pagination, a timestamp format or a write requirement, while its published schema stays the same; in npm, about two thirds of documented breaking changes are behavioural rather than signature changes~\cite{kong2025npm}.
Section~\ref{sec:why} gives the evidence that such failures are frequently reported, that agents often adopt the wrong values and LLM judges detect false success poorly, and that monitors which catch them do not fix the tool.

\fiks{} turns the violation into a reviewable fix.
A violation seen at the proxy already contains most of a reproduction: the exact arguments, the raw upstream exchange and the property that failed.
Writing a valid reproduction test is the bottleneck of test-driven repair~\cite{tdflow}, and fail-to-pass tests can still be lax~\cite{tan2026coharden}.
\fiks{} therefore (i)~compiles the trace into a test that must fail on the current code \emph{for the stated reason}, (ii)~gives that test to a tool-restricted coding agent, and (iii)~runs every gate, including CI on the exact commit, \emph{before} a pull request is opened.

\section{Why this tool should exist: the evidence}
\label{sec:why}

Five lines of published evidence and one informal practitioner discussion motivate \fiks{} (Table~\ref{tab:evidence}).

\paragraph{Agents depend on tool results, and silent tool faults are real.} Agents are meant to obtain ground truth from the environment, such as tool results, at each step~\cite{anthropic2024agents}. In a survey of 41 practitioners, tool-response handling (malformed, incomplete or semantically unusable output after a \emph{successful} call) was the most frequently reported MCP fault type (66.67\%, ahead of documentation at 64.52\%), and the authors recommend validating responses after successful invocation~\cite{taraghi2026realfaults}. An analysis of 833 MCP fault threads found servers returning well-formed success responses despite incorrect behaviour~\cite{owotogbe2026mcpfaults}. The MCP reference memory server silently dropped new observations sent for existing entities (47 of 130 agent runs)~\cite{mcp-memory-4887}, and an executable-contract audit found seven defects in the tools of agent benchmarks, including success messages for writes that never happened~\cite{bellibatlu2026contractaudit}.

\paragraph{Agents do not catch them, and neither do observers.} When a production API silently accepts an invalid value, agents rarely notice (12\%) and never repair it; they tell the user nothing exists (41\%) or invent a figure (12\%)~\cite{li2026silentprobe}. Agents adopt corrupted but plausible tool returns at high rates, up to 68\% for web search~\cite{yang2026overreliance}; implicit tool failures cause the sharpest recovery drops~\cite{zhu2026toolmaze}; and agents given empty or malformed success payloads fabricated results in 56.6\% of valid responses~\cite{singh2026scapegoats}. Detection from the outside is also hard: no LLM-judge configuration exceeded AUROC 0.65 at detecting false success on $\tau^2$-bench~\cite{advani2026falsesuccess}, gray failure is defined by differential observability: a system's own failure detectors may not notice a problem its applications experience~\cite{huang2017grayfailure}, and agent frameworks can alter valid MCP results after the wire~\cite{patodiya2026postwire}.

\paragraph{Upstream behaviour drifts while schemas stay the same.} In npm, about two thirds of documented breaking changes are behavioural rather than signature changes~\cite{kong2025npm}. Real providers ship changes that clients misread without any error: GitHub treats enum additions as non-breaking~\cite{github-breaking-changes}, an LLM gateway turned a safety refusal into a normal completion through a default branch for unknown enum values~\cite{litellm-23899}, and a popular finance wrapper documents that its upstream sometimes returns prices 100$\times$ wrong (dollars vs cents) and ships a repair step for them~\cite{yfinance-price-repair}. Production ML practice warns that a source-system upgrade can change a feature's meaning without producing values strange enough to trigger monitoring~\cite{breck2017mltestscore}. A specification diff of an unchanged document reports nothing~\cite{oasdiff-breaking}; MCP output-schema validation is a client-side recommendation~\cite{mcp-spec-2026-07-28-tools}; and static analysis of 1{,}899 MCP servers flags bug patterns but not behavioural, data-dependent faults~\cite{hasan2025mcpfirstglance}.

\paragraph{Detection without repair does not last.} Outcome monitors give the running agent recovery affordances but explicitly do not repair the tool~\cite{panthi2026outcomemonitors}. In data validation, over-alerting leads users to ignore alerts, and an alert's value is whether it is actionable and gets fixed~\cite{polyzotis2018lifecycle}; engineers silenced and eventually abandoned a completeness check that raised too many false alarms~\cite{shankar2023brokendata}. Error-tracking autofix starts from errors and, for automatic runs, needs recurrence (at least 10 events in 14 days), with reproduction tests only on request~\cite{sentry-seer-issue-fix}; PostHog's agent adds a regression test but does not require it to fail first, and fixes CI after opening the pull request~\cite{posthog-anatomy-pr}.

\paragraph{Repair needs a valid test and green CI.} Writing a true reproduction test is the bottleneck of test-driven repair~\cite{tdflow}; fail-to-pass tests can be too lax to reject wrong patches~\cite{tan2026coharden} or admit partial ones~\cite{swe-doctor}; and industrial agentic repair starts from an existing failing test rather than from a runtime observation~\cite{maddila2025metaagent}. On the review side, each failed CI check on an agent-authored pull request is associated with about 15\% lower merge odds~\cite{ehsani2026failedagenticprs}. A runtime violation supplies the test's inputs and oracle; running CI before the pull request opens addresses the second point.

\paragraph{Practitioners are asking for it.} In an informal Reddit discussion of benchmarks practitioners wish existed (accessed 2026-10-24)~\cite{reddit2026benchmarkwish}, several replies asked for related settings: how an agent handles a tool that returns garbage or an MCP server that dies mid-task; results the agent must decide whether to trust; writes whose response is lost or whose error claims failure although the write happened; scoring the final state of the world instead of the final answer; and agents that fail confidently while passing demos. This thread is self-selected and unverified (one respondent described itself as an AI agent), so we treat it as motivation, not as evidence of prevalence. It also marks our scope: \fiks{} addresses silently wrong successful results and unpersisted writes (\texttt{readAfterWrite}); it does not address servers that die mid-task, error results whose action actually succeeded, lost responses, timeouts, duplicated side effects after retries, permission drift or approvals that no longer cover an action.

\paragraph{The gap.} In the sources we reviewed (searched up to 2026-10-21), robustness benchmarks measure how agents cope with faulty tool output~\cite{zhu2026toolmaze,yang2026overreliance}, monitors warn the agent~\cite{panthi2026outcomemonitors,verimcp}, and repair products start from errors~\cite{sentry-seer-issue-fix,devin-oncall}; we found no open system or benchmark that measures whether a silent tool failure leads to a tested, reviewed fix of the tool itself (\S\ref{sec:related}).

\section{Problem definition}
\label{sec:problem}

Let a tool $\tau$ map arguments $x$ to a result $r=\tau(x)$ by calling an upstream service $U$; the call produces an upstream exchange $e=(\mathrm{req},\mathrm{resp})$.
A \emph{silent failure} is a call where $r$ is a well-formed success (no exception, no \texttt{isError}, valid against the declared \texttt{outputSchema}) but $r$ misstates the state of $U$.
The MCP specification lets a tool declare an \texttt{outputSchema} for its structured content, with output validation left to clients~\cite{mcp-spec-2026-07-28-tools}; a schema can check shape, not whether a price is in dollars or cents.

We focus on \emph{upstream behavioural drift}: $U$ changes at time $t_0$ while its published specification and $\tau$'s code do not.
From $t_0$ on, every call that touches the changed behaviour is silently wrong, for every agent, until $\tau$ is fixed.
Three properties make this setting tractable for a closed loop:
(a)~the violation is observable per call, because the proxy sees both $r$ and $e$;
(b)~the trace $(x, e, r, \text{property})$ is a deterministic reproduction once $e$ is replayed;
(c)~the fix belongs to $\tau$'s repository, so it can be proposed as a pull request and reviewed.

\subsection{Outcome contracts and receipts}
A contract is a per-tool list of invariants evaluated on each successful result (Table~\ref{tab:vocab}).
Most kinds resemble schema and anomaly checks in data validation systems~\cite{tfdv-2019}; two kinds use the proxy's position between tool and upstream.
\texttt{equalsUpstream} compares a result field with the field the upstream actually sent in the same call, and \texttt{readAfterWrite} re-reads a created resource from the upstream to confirm a write persisted.
Each verdict is \emph{verified}, \emph{violated} or \emph{unverifiable}.
The proxy attaches a receipt to the result in three places: MCP \texttt{\_meta}, a final text block, and a field in \texttt{structuredContent}, because some clients show the model only the structured content.
A receipt states the violated property, the upstream facts the proxy observed, and what the agent should not do with the value. The receipt for the pilot's renamed-price drift reads:
\begin{lstlisting}
[fiks] VIOLATED get_product: price is null, but p-1001 should have one; vendor sent unit_amount = 1199 (in 20-2000 USD). Don't say there is no price; if you use the vendor value, say unconfirmed.
\end{lstlisting}

\subsection{Trace, reproduction and the F gate}
On a violation the proxy stores a trace: tool, arguments, the raw upstream requests and responses recorded by an HTTP tap, the contract and the violated property ids.
\fiks{} generates a test in the server's own repository that replays the recorded upstream exchange through the server's real code and asserts the contract.
The \textbf{F gate} accepts the test only if it fails on the current code on every one of several runs (three in the current code; two in the earliest pilot runs, Table~\ref{tab:loop}), and the first failure line names exactly the target property ids; a test that fails for another reason, or passes, is rejected.
This makes ``fails for the stated reason'' a deterministic check that needs no reference patch, unlike fail-to-pass validation against a gold patch~\cite{mundler2024swtbench} or heuristic checks on the failure~\cite{otter}.

\subsection{Repair and gates}
A coding agent (Claude Agent SDK; \repairModel{} in the pilot) receives the violation, the trace and the failing test in an isolated git worktree. In the pilot (prompt as first committed in \texttt{8c7daa8}, unchanged at \texttt{\fiksSha}), the prompt also stated that the vendor had changed its behaviour without changing its published spec, included the tool's contract, each raw upstream response (truncated to 800 characters) and, when one existed, the path of the v1 recording of the same call, and gave two general notes: that responses carry a vendor version header with its dates before and after the change, and that a fix may change which requests the tool sends (``a new header, extra pages''). These notes hint at the shape of the D1, D3 and D4 fixes.
A tool-permission callback lets it write only under \texttt{src/}, run only the project's typecheck, lint and test commands, and read only inside the worktree; tests, fixtures and traces are hashed at the snapshot, and any change to them fails the run.
When a correct fix changes upstream requests (for example, a new required header), \fiks{} itself re-records the affected fixtures from the committed recordings with a frozen clock, in a separate commit containing only re-recordings.
The \textbf{P gate} then requires the repro to pass, together with the full contract suite, every stored trace, typecheck and lint.
\fiks{} pushes the branch, waits for CI on that exact commit, and opens a pull request only if CI is green; if the pull request's head differs from the commit that passed CI, it is closed.
The pull request body states what broke, the trace, the test, the diff, before/after results and the gate outcomes, and says that a green suite is not a proof of correctness.
\fiks{} never merges. After a merge, \texttt{fiks confirm} re-runs each repaired call live and replays every stored trace.

\subsection{Detection and false alarms}
In the drift phase, \violatedCallsB{} of \callsB{} tool calls received a violated receipt, covering the violated properties of all five drifts (D1 \texttt{items.price.range}, D2 \texttt{price.notNull}, D3 \texttt{readAfterWrite}, D4 \texttt{countMatchesTotal}, D5 \texttt{created\_at} freshness and upstream agreement).

These bounds are weak: the pilot's clean traffic is small and comes from the same six tasks the contracts were written against.

\subsection{Agent outcomes}

\subsection{A negative result: receipt wording}
Receipts are part of the method. Our first wording (v1) stated the violation and told the agent not to quote the flagged value; apart from the timestamp drift, whose receipt is unchanged in v2, it neither gave the upstream value the tool had dropped nor suggested a next step other than telling the user the value was unavailable or unconfirmed.
With it, pass$^5$ was \pFiveBold{} against \pFiveBdold{} without \fiks{} on the same day (Table~\ref{tab:receipts}; \pairLossesOld{} tasks worse, \pairWinsOld{} better, sign test $p=\pairPOld$): the agent declined \declinedBold{} times (all trials of T1, T2 and T3; the T3 declines also occur without \fiks) and \noAnswerBold{} times gave no answer.
The second wording (v2) adds the upstream value the tool dropped, labelled unconfirmed, and next steps. We changed the wording after seeing these results, so the v2 numbers are post hoc and need the independent test in \S\ref{sec:protocol}.

\section{Related work and novelty boundary}
\label{sec:related}

\paragraph{Silent failures and agent benchmarks.} MCP fault studies classify silent faults from issue threads but do not reproduce or repair them~\cite{owotogbe2026mcpfaults}. The robustness studies in \S\ref{sec:why} evaluate how the agent responds to bad tool output~\cite{singh2026scapegoats,zhu2026toolmaze,yang2026overreliance}, not how the tool gets fixed, and $\tau$-bench's tools are deterministic functions over JSON databases~\cite{yao2024taubench}.

\paragraph{Runtime monitors.} Outcome Monitors check results and give the agent recovery affordances, explicitly without repairing the tool~\cite{panthi2026outcomemonitors}; verimcp re-derives outcomes after git, file and CI calls~\cite{verimcp}; a tool wrapper combining postcondition verification, verify-before-retry and idempotency keys reduced duplicate actions in simulation~\cite{mansoor2026verifiedtoolcalls}. Action-side enforcement such as AgentSpec checks planned actions rather than results~\cite{agentspec}. \fiks{}'s receipt step belongs to this line and is not new on its own.

\paragraph{Specification, contract and data validation.} Consumer-driven contracts need the provider to run consumer pacts~\cite{pact-how-it-works}; schema-derived fuzzing finds schema violations~\cite{hatfielddodds2022schemathesis}. Large-scale studies count breaking changes in library APIs~\cite{xavier2017apibreak,kong2025npm}. Data validation systems enforce similar presence, range and distribution checks on batches~\cite{tfdv-2019}, and invariant inference goes back to Daikon~\cite{daikon}. Record/replay tools turn captured traffic into regression tests whose oracle is the old response~\cite{keploy}; that oracle encodes the bug when the recording is made after the drift.

\paragraph{Reproduction and repair.} Issue-to-test generation is hard and its validity is judged by fail-to-pass execution~\cite{libro,mundler2024swtbench,otter}. In a self-healing agent harness 55\% of gate-rejected instruction changes improved their trigger while regressing a protected case~\cite{tayebati2026selfhealingharness}. Repair systems start from issues~\cite{swe-agent,agentless}, compile errors after a dependency bump~\cite{reyes2025byam}, or an upstream breaking change with no localizing failing test~\cite{yang2026deprepair}. Structured upstream evidence helps dependency repair while raw evidence hurts~\cite{yang2026deprepair}; \fiks{} gives the agent a failing test built from the trace, although the pilot prompt also included the raw upstream responses (\S\ref{sec:design}).

\paragraph{Production-driven and commercial loops.} ClearView patched deployed software from learned invariants~\cite{perkins2009clearview}; Itzal validated production-driven patches on traffic~\cite{durieux2016itzal}; SapFix shipped detect--test--repair with human approval~\cite{marginean2019sapfix}. In 2026, observability and alerting products open fix pull requests from errors, incidents or LLM scans and iterate CI after opening~\cite{sentry-seer-issue-fix,posthog-anatomy-pr,devin-oncall,langsmith-changelog-2026}, and some measure recurrence after fixes~\cite{cleric-verifying-fixes}. AegisFlow detects silent pipeline drift statistically and deploys validated patches autonomously for pre-approved failure classes~\cite{awan2026aegisflow}. A granted patent claims language-model repair of a detected issue from its error information, with dependent claims adding a pull request accompanied by a software test~\cite{msft-us12711009}.

\paragraph{What is and is not new.} Table~\ref{tab:matrix} compares the closest systems by loop step, from their documentation or papers. Each step exists somewhere. In the sources we reviewed (searched up to 2026-10-21; patent databases only partly searched), we found no system that combines: a trigger that is a deterministic contract violation in a \emph{successful} tool result, checked per call against the raw upstream exchange; a committed test that must fail first for the named property; and all gates, including CI on the exact commit, before the pull request opens, with a receipt to the agent while the fix is pending. We claim only that combination, and the pilot does not yet show that it outperforms a composition of existing parts; that is the question of \S\ref{sec:protocol}.

\section{Confirmatory protocol (pre-registration draft)}
\label{sec:protocol}

The draft pre-registration is \texttt{paper/prereg/PREREG.md}, sourced from \texttt{paper/PLAN.md}; it becomes binding only when tagged \texttt{prereg-v1}, and amendments made before that are logged in \texttt{PLAN.md} \S0.B. It was produced by competing designs, a judge panel and repeated adversarial critique, and its power numbers are recomputed by script. No confirmatory run has been performed, and part of the required tooling is still being built. The protocol compares \fiks{} with two strong alternatives built on the same monitor, model, budget and sandbox: \textbf{L1}, the same agent and gates with a pre-PR replay of the triggering trace but no visible reproduction test; and \textbf{COMP}, the strongest documented composition, monitor $\rightarrow$ alert $\rightarrow$ coding agent $\rightarrow$ PR $\rightarrow$ CI with source-run replay. Four hypotheses form the confirmatory family (Holm, FWER 0.05):
\begin{description}
  \item[H1 (trigger).] On a frame (fixed in the draft) of at least 1{,}500 blind-authored catalog entities over two domains, fewer than 2\% of entities give rise to any false positive (exact binomial test), with fewer than 1\% of inputs flagged.
  \item[H2 (artifact).] Over a fixed, arm-independent patch pool graded by a held-out oracle, the trace-derived named-property repro has higher balanced accuracy than a fail-first repro written by a coding agent from the same alert, raw trace and replay helper.
  \item[H3 (visible repro).] \fiks{} exposes fewer green-but-incorrect pull requests than L1, with a correct-PR loss no larger than 0.10 (intersection--union test with a direction guard).
  \item[H4 (vs composition).] The same comparison against COMP.
\end{description}
Drifts are authored blind to the contracts by a separate process and applied by a third-party response-rewriting injector; benign upstream evolution, mutation operators frozen before contracts, four real silent-failure bugs in public MCP servers, to be reproduced in private clones, and an adversarial-trace security suite are exploratory arms. Expected losses are stated in the draft as well: out-of-vocabulary string corruption, legitimate evolution that a fixed contract misreads as a fault, and cases where issue text already explains the bug.

\section{Threats to validity and limitations}
\label{sec:limits}

\paragraph{Circularity.} The author wrote the drifts, the contracts and the tasks; detection of D1--D5 is therefore close to a construction property. Mutation-based oracle assessment and real faults are needed to measure what contracts miss~\cite{jahangirova2016oracle,just2014mutants}, and runtime contract vocabularies have known blind spots on out-of-vocabulary faults~\cite{panthi2026outcomemonitors}.
\paragraph{Scale and statistics.} \nTasks{} tasks and \kTrials{} trials cannot support task-level significance; trial-level intervals ignore clustering~\cite{bowyer2025clt}. The false-alarm bound comes from \vOneCalls{} clean calls.
\paragraph{Partial or overfitted patches.} A green suite shows the repro and the recorded contracts pass; it does not prove correctness~\cite{swe-doctor,tan2026coharden}. During development, an adversarial verifier showed that two wrong fixes pass the test suite: a D2 fix that returns a constant in-range price, and a D1 fix that clamps prices to the range ceiling. The pilot measured no held-out oracle.
\paragraph{Prompt hints.} The pilot repair prompt (\S\ref{sec:design}) named the failure class, included the contract and the raw upstream responses, and its general notes point toward the D1, D3 and D4 fixes; the pilot fixes are small, and one-attempt success on these drifts may not carry over to repairs without such context.
\paragraph{Security.} The repair agent reads attacker-controllable vendor bytes and its code runs in tests. Restricting terminal access does not stop injected agents from writing malicious source~\cite{liu2025aishelljack}, test-passing patches can hide vulnerabilities~\cite{chen2025swexploit}, and injection through tool output is measurable~\cite{debenedetti2024agentdojo,bouras2026capscope}. In the pilot the agent ran without an OS or network sandbox; a container backend and an injection suite are part of the protocol, not of these results.
\paragraph{Legitimate evolution.} A fixed contract cannot tell a vendor fault from an intended change; the pilot always proposed a code fix. A contract-update outcome is designed but unevaluated.
\paragraph{Pilot build differences.} \nFTwoRuns{} of \nDrifts{} F gates ran twice rather than three times; all \nDrifts{} repairs and the receipt-v1 runs used uncommitted code; and every repair was triggered by a scripted call, not by agent traffic.
\paragraph{External validity.} One mock vendor, one server, one model family (Claude) for both bench and repair, and seeded rather than organic drift. Merged pull requests were merged by an AI assistant at the owner's request without line-by-line review, so they say nothing about maintainer acceptance.

\section{Conclusion}
\fiks{} shows that a silent tool failure caught by the proxy on a call against a drifted vendor can be turned, within minutes, into a named-property failing test and a gate-passing pull request against the tool. The pilot demonstrates feasibility on seeded drifts; it does not show that the loop beats a composition of existing monitors and coding agents, that its contracts generalize beyond the drifts they were written for, or that its pull requests would be accepted. The draft protocol is designed to answer the first two questions; maintainer acceptance needs a separate study.
