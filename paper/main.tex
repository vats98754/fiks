\begin{abstract}
LLM agents' tools can fail silently: a Model Context Protocol (MCP) server returns a well-formed success whose content is wrong, for example after its upstream API changes behaviour but not its schema.
Such failures occur and agents often adopt the wrong values; a schema checks shape, not meaning. Runtime monitors warn the current agent, but the tool stays broken for later ones.
We present \fiks, which turns a silent tool failure into a reviewable fix.
A proxy checks each successful MCP result against an outcome contract (including agreement with the raw upstream exchange and read-after-write) and returns a receipt to the agent.
A violation becomes a deterministic reproduction test that must fail on the current code for the named property; a tool-restricted coding agent repairs the server; and a pull request is opened only after that test, the contract suite, stored traces, typecheck, lint and CI on the exact commit pass. \fiks{} never merges.
In a pilot with \nDrifts{} seeded drifts on a mock vendor whose OpenAPI document is unchanged, \fiks{} flagged all \nDetected, built a valid fail-first test for each and got a green-CI pull request in one attempt per drift (\minsMin--\minsMax{} min from violation to PR; \$\costMin--\$\costMax{} per repair at API prices).
In a \nTasks-task, \kTrials-trial agent bench, pass$^5$ was \pFiveBd{} without \fiks, \pFiveB{} with receipts and \pFiveC{} after the fixes were merged; the pilot is too small to establish the receipt effect (sign test $p=\pairP$), and an earlier receipt wording did worse than no monitor (also not significant).
In exploratory follow-ups, contracts caught \expDetectRecallOutsideSilent{} of silent response mutants from operators with no matching contract check; in a sandboxed ablation (\expRunsTotal{} repairs), \expLiveFiks{} repairs with \fiks's inputs passed a live check against \expLiveAlert{} given a prose alert and trace ($p=\expSignFiksVsAlertP$), whose gates kept \expGatesPassLiveFailAlert{} patches leaving the violation in place.
We release a draft pre-registration for a confirmatory study not yet run.
\end{abstract}

\section{Introduction}
\label{sec:intro}

When a tool fails loudly, with an exception or an error result, the agent can retry, an error tracker can file an issue, and a coding agent can be pointed at the stack trace~\cite{sentry-seer-issue-fix,devin-oncall}.
When a tool fails silently, none of this happens: a Model Context Protocol (MCP) server returns a well-formed success whose content is wrong.
One cause, and the one this paper targets, is upstream drift: the vendor API behind the server changes a unit, a field name, pagination, a timestamp format or a write requirement, while its published schema stays the same; in npm, about two thirds of documented breaking changes are behavioural rather than signature changes~\cite{kong2025npm}.
Such failures are frequently reported, agents often adopt the wrong values, LLM judges detect false success poorly, and monitors that catch them do not fix the tool (\S\ref{sec:why}).

\fiks{} turns the violation into a reviewable fix.
A violation seen at the proxy already contains most of a reproduction: the exact arguments, the raw upstream exchange and the property that failed.
Writing a valid reproduction test is the bottleneck of test-driven repair~\cite{tdflow}, and fail-to-pass tests can still be lax~\cite{tan2026coharden}.
\fiks{} therefore (i)~compiles the trace into a test that must fail on the current code \emph{for the stated reason}, (ii)~gives that test to a tool-restricted coding agent, and (iii)~runs every gate, including CI on the exact commit, \emph{before} a pull request is opened.

\paragraph{Contributions.}
\begin{enumerate}
  \item \textbf{A loop and its gate placement} (\S\ref{sec:design}): per-call outcome contracts on successful MCP results, a receipt to the agent, trace capture with the raw upstream exchange, a named-property fail-first reproduction, gated repair, and a pull request that is never merged automatically.
  \item \textbf{Gates hardened against the repair agent} (\S\ref{sec:hardening}): five attacks an adversarial agent mounted on the gates, each closed and kept as a regression test, and a seed suite that rejects eight known wrong fixes.
  \item \textbf{A pilot evaluation} (\S\ref{sec:pilot}) on \nDrifts{} seeded drifts, with every number regenerated by a script from committed logs, including a negative result on receipt wording, and three exploratory follow-ups: an LLM-free detection sweep with response mutations, a repair-input ablation (agent commands and gates in a container) judged after repair by the reproduction test and a live check in a fresh checkout, and an injection smoke test (\S\ref{sec:exp}).
\end{enumerate}
Section~\ref{sec:related} states what is not new, and Section~\ref{sec:protocol} summarizes a draft protocol for the confirmatory study.

\section{Motivating evidence}
\label{sec:why}

Table~\ref{tab:evidence} pairs each finding with the design response it motivates.

\paragraph{Silent tool faults occur.} Agents are meant to obtain ground truth from the environment, such as tool results, at each step~\cite{anthropic2024agents}. In a survey of 41 practitioners, tool-response handling after a \emph{successful} call (malformed, incomplete or semantically unusable output) was the most frequently reported MCP fault type (66.67\%; documentation 64.52\%), and the authors recommend validating responses after successful invocation~\cite{taraghi2026realfaults}; an analysis of 833 MCP fault threads found servers returning well-formed success responses despite incorrect behaviour~\cite{owotogbe2026mcpfaults}. The MCP reference memory server silently dropped new observations sent for existing entities (47 of 130 agent runs)~\cite{mcp-memory-4887}, and an executable-contract audit found seven defects in agent-benchmark tools, including success messages for writes that never happened~\cite{bellibatlu2026contractaudit}.

\paragraph{Agents and observers miss them.} When a production API silently accepts an invalid value, agents rarely notice (12\%) and never repair it; they tell the user nothing exists (41\%) or invent a figure (12\%)~\cite{li2026silentprobe}. Agents adopt corrupted but plausible returns at rates up to 68\% for web search~\cite{yang2026overreliance}, implicit tool failures cause the sharpest recovery drops~\cite{zhu2026toolmaze}, and agents given empty or malformed success payloads fabricated results in 56.6\% of valid responses~\cite{singh2026scapegoats}. No LLM-judge configuration exceeded AUROC 0.65 at detecting false success on $\tau^2$-bench~\cite{advani2026falsesuccess}; in gray failure a system's own failure detectors may not notice a problem its applications experience~\cite{huang2017grayfailure}; and agent frameworks can alter valid MCP results after the wire~\cite{patodiya2026postwire}.

\paragraph{Behaviour drifts under an unchanged schema.} Providers ship changes that clients misread without any error: GitHub treats enum additions as non-breaking~\cite{github-breaking-changes}, an LLM gateway turned a safety refusal into a normal completion through a default branch for unknown enum values~\cite{litellm-23899}, and a popular finance wrapper documents upstream prices that are sometimes 100$\times$ wrong (dollars vs cents) and ships a repair step for them~\cite{yfinance-price-repair}. Production ML practice warns that a source-system upgrade can change a feature's meaning without tripping monitoring~\cite{breck2017mltestscore}. MCP output-schema validation is a client-side recommendation~\cite{mcp-spec-2026-07-28-tools}, and static analysis of 1{,}899 MCP servers flags bug patterns but not behavioural, data-dependent faults~\cite{hasan2025mcpfirstglance}.

\paragraph{Existing repair loops start elsewhere.} Error-tracking autofix starts from errors and, for automatic runs, needs recurrence (at least 10 events in 14 days), with reproduction tests only on request~\cite{sentry-seer-issue-fix}; PostHog's agent adds a regression test but does not require it to fail first, and fixes CI after opening the pull request~\cite{posthog-anatomy-pr}. Fail-to-pass tests can admit partial patches~\cite{swe-doctor}, industrial agentic repair starts from an existing failing test rather than from a runtime observation~\cite{maddila2025metaagent}, and each failed CI check on an agent-authored pull request is associated with about 15\% lower merge odds~\cite{ehsani2026failedagenticprs}.

\paragraph{Practitioner requests.} In an informal Reddit discussion of benchmarks practitioners wish existed (accessed 2026-10-24)~\cite{reddit2026benchmarkwish}, several replies asked for related settings, among them tools that return garbage, results the agent must decide whether to trust, writes whose response is lost or whose error claims failure although the write happened, and agents that fail confidently while passing demos. The thread is self-selected and unverified (one respondent described itself as an AI agent), so it is motivation, not evidence of prevalence. \fiks{} addresses silently wrong successful results and unpersisted writes (\texttt{readAfterWrite}); it does not address servers that die mid-task, error results whose action actually succeeded, lost responses, timeouts, duplicated side effects after retries, permission drift or approvals that no longer cover an action.

\paragraph{The gap.} In the sources we reviewed (searched up to 2026-10-21), robustness benchmarks measure how agents cope with faulty tool output~\cite{zhu2026toolmaze,yang2026overreliance}, monitors warn the agent~\cite{panthi2026outcomemonitors,verimcp}, and repair products start from errors~\cite{sentry-seer-issue-fix,devin-oncall}; we found no open system or benchmark that measures whether a silent tool failure leads to a tested, reviewed fix of the tool itself (\S\ref{sec:related}).

\section{Problem definition}
\label{sec:problem}

Let a tool $\tau$ map arguments $x$ to a result $r=\tau(x)$ by calling an upstream service $U$; the call produces an upstream exchange $e=(\mathrm{req},\mathrm{resp})$.
A \emph{silent failure} is a call where $r$ is a well-formed success (no exception, no \texttt{isError}, valid against the declared \texttt{outputSchema}) but $r$ misstates the state of $U$.
The MCP specification lets a tool declare an \texttt{outputSchema} for its structured content, with output validation left to clients~\cite{mcp-spec-2026-07-28-tools}; a schema can check shape, not whether a price is in dollars or cents.

We focus on \emph{upstream behavioural drift}: $U$ changes at time $t_0$ while its published specification and $\tau$'s code do not.
From $t_0$ on, every call that touches the changed behaviour is silently wrong, for every agent, until $\tau$ is fixed.
Three properties make this setting tractable for a closed loop:
(a)~the violation is observable per call, because the proxy sees both $r$ and $e$;
(b)~the trace $(x, e, r, \text{property})$ is a deterministic reproduction once $e$ is replayed;
(c)~the fix belongs to $\tau$'s repository, so it can be proposed as a pull request and reviewed.

\subsection{Outcome contracts and receipts}
A contract is a per-tool list of invariants evaluated on each successful result (Table~\ref{tab:vocab}).
Most kinds resemble schema and anomaly checks in data validation systems~\cite{tfdv-2019}; two kinds use the proxy's position between tool and upstream.
\texttt{equalsUpstream} compares a result field with the field the upstream actually sent in the same call, and \texttt{readAfterWrite} re-reads a created resource from the upstream to confirm a write persisted.
Each verdict is \emph{verified}, \emph{violated} or \emph{unverifiable}.
The proxy attaches a receipt to the result in three places: MCP \texttt{\_meta}, a final text block, and a field in \texttt{structuredContent}, because some clients show the model only the structured content.
A receipt states the violated property, the upstream facts the proxy observed, and what the agent should not do with the value. The receipt for the pilot's renamed-price drift reads:
\begin{lstlisting}
[fiks] VIOLATED get_product: price is null, but p-1001 should have one; vendor sent unit_amount = 1199 (in 20-2000 USD). Don't say there is no price; if you use the vendor value, say unconfirmed.
\end{lstlisting}

\subsection{Trace, reproduction and the F gate}
On a violation the proxy stores a trace: tool, arguments, the raw upstream requests and responses recorded by an HTTP tap, the contract and the violated property ids.
\fiks{} generates a test in the server's own repository that replays the recorded upstream exchange through the server's real code and asserts the contract.
The \textbf{F gate} accepts the test only if it fails on the current code on every one of several runs (three in the current code; two in the earliest pilot runs, Table~\ref{tab:loop}), and the first failure line names exactly the target property ids; a test that fails for another reason, or passes, is rejected.
This makes ``fails for the stated reason'' a deterministic check that needs no reference patch, unlike fail-to-pass validation against a gold patch~\cite{mundler2024swtbench} or heuristic checks on the failure~\cite{otter}.

\subsection{Repair and gates}
A coding agent (Claude Agent SDK; \repairModel{} in the pilot) receives the violation, the trace and the failing test in an isolated git worktree. In the prompt as first committed in \texttt{8c7daa8} and unchanged at \texttt{\fiksSha} (the D1--D3 and D5 pilot repairs ran from an uncommitted tree that predates that commit, and their prompts were not logged), the prompt also stated that the vendor had changed its behaviour without changing its published spec, included the tool's contract, each raw upstream response (truncated to 800 characters) and, when one existed, the path of the v1 recording of the same call, and gave two general notes: that responses carry a vendor version header with its dates before and after the change, and that a fix may change which requests the tool sends (``a new header, extra pages''). These notes hint at the shape of the D1, D3 and D4 fixes.
A tool-permission callback lets it write only under \texttt{src/}, run only the project's typecheck, lint and test commands, and read only inside the worktree; tests, fixtures and traces are hashed at the snapshot, and any change to them fails the run.
When a correct fix changes upstream requests (for example, a new required header), \fiks{} itself re-records the affected fixtures from the committed recordings with a frozen clock, in a separate commit containing only re-recordings.
The \textbf{P gate} then requires the repro to pass, together with the full contract suite, every stored trace, typecheck and lint.
\fiks{} pushes the branch, waits for CI on that exact commit, and opens a pull request only if CI is green; if the pull request's head differs from the commit that passed CI, it is closed.
The pull request body states what broke, the trace, the test, the diff, before/after results and the gate outcomes, and says that a green suite is not a proof of correctness.
\fiks{} never merges. After a merge, \texttt{fiks confirm} re-runs each repaired call live and replays every stored trace.

\subsection{Hardening the gates against the repair agent}
\label{sec:hardening}
The repair agent is untrusted: its code runs during the gates and can try to change what they see. During development a separate agent attacked the gates as an adversary over six rounds and found five ways through: committing to bypass the write guard; having code under test rewrite \fiks{}'s re-recordings while the gates run; a detached helper process that edited them before \fiks{} hashed them; steering the re-recording by changing the vendor profile it read from disk; and a planted symbolic link that redirected which committed recording was read. Each is closed and kept as a regression test that now ends in \texttt{gate\_failed} with no pull request. \fiks{} also disables git hooks for its own git calls and treats a refused re-recording as a failed gate.

A second suite checks that the seed contracts accept real fixes and reject eight wrong fixes an agent might plausibly write (Table~\ref{tab:seed}); \S\ref{sec:limits} lists two wrong fixes that still pass.

\subsection{Detection and false alarms}
In the drift phase, \violatedCallsB{} of \callsB{} tool calls received a violated receipt, covering the violated properties of all five drifts (D1 \texttt{items.price.range}, D2 \texttt{price.notNull}, D3 \texttt{readAfterWrite}, D4 \texttt{countMatchesTotal}, D5 \texttt{created\_at} freshness and upstream agreement).
On clean v1 traffic, \vOneViolated{} of \vOneCalls{} calls were flagged (Wilson 95\% upper bound \vOneFpUpper{} per call; \vOneTrialFpUpper{} per trial over \trialsA{} trials).
These bounds are weak: the pilot's clean traffic is small and comes from the same six tasks the contracts were written against.

\subsection{The repair loop}
Table~\ref{tab:loop} reports the loop for each drift. Each loop was triggered by a fixed one-call scenario against vendor v2, not by the bench agent's calls.
All \nReproValid{} reproductions passed the F gate with the named property ids (\nFThreeRuns{} on three runs; \nFTwoRuns{}, run on 2026-10-18, on two runs, the setting used then), all \nOneAttempt{} repairs succeeded in one agent attempt (\turnsMin--\turnsMax{} turns, median \turnsMedian), and all \nPrGreen{} pull requests had green CI before opening.
Total repair cost was \$\costTotal{} at API list prices; the runs used a subscription token, so this is an estimate, not a bill.
After the \nPrsMerged{} pull requests (and the harness pull request) were merged by an AI coding assistant on the owner's account at the owner's request, without line-by-line review, \texttt{fiks confirm} found each drift resolved (\nConfirmed/\nDrifts).
Across the pilot and later demonstration runs, \fiks{} opened \nPrs{} repair pull requests, all with green checks; \nPrsMerged{} were merged, \nPrsDemoOpen{} demonstration pull requests target throw-away branches and remain open, and \nPrsClosed{} was a duplicate opened by an operator error and closed.
These merges are not evidence of maintainer acceptance, which large-scale studies of agent pull requests measure separately~\cite{ehsani2026failedagenticprs}.

\subsection{Exploratory extensions}
\label{sec:exp}
After the pilot we ran three small extensions under a plan committed before any of them ran (\path{paper/EXP-PLAN.md}). They are exploratory and separate from the pre-registration draft. Every count below is computed by a script from, or read directly off, the per-run logs committed under \path{bench/results/exp/}.

\paragraph{E-B: detection without an LLM.} \emph{Clean traffic.} Every product (\texttt{get\_product}), every category and a fixed query list (\texttt{search\_products}) and the seed order (\texttt{get\_order}), sent through the proxy to vendor v1: \expDetectCleanViolated{} of \expDetectCleanCalls{} read-only calls were flagged (\expDetectCleanEntities{} entities; Wilson 95\% upper bound \expDetectWilsonUpperCall{} per call and \expDetectWilsonUpperEntity{} per entity). \emph{Response mutations.} Each response operator (M1--M14) and benign operator (B1--B4) of the \fiks{} mutation catalog was applied, with one seed, to every recorded v1 upstream response of those calls it applies to, and replayed offline through the unmodified server and the contracts (Table~\ref{tab:detect}); replaying the unmutated recordings reproduced all \expDetectControlsMatch{} logged verdicts. Of \expDetectMutants{} mutants, \expDetectMutantsToolError{} made the tool return an error (a loud failure, outside \fiks's scope) and \expDetectMutantsFlagged{} were flagged, \expDetectRecallSilent{} of the \expDetectMutantsSilent{} mutants that still returned success. Recall sits almost entirely in operators whose coupled contract kind the shop contracts contain: \expDetectRecallCheckedSilent{} (\expDetectFlaggedChecked{} of \expDetectMutantsCheckedSilent) of silent mutants from those operators, against \expDetectRecallOutsideSilent{} (\expDetectFlaggedOutside{} of \expDetectMutantsOutsideSilent) from the others, which include unknown enum values (M10: the contracts have no enum check, and none was flagged). Unit scaling was caught on prices and totals but not on stock counts or order-line unit prices (\expDetectFlaggedMOne{} and \expDetectFlaggedMTwo{} of \expDetectApplicableMOne{} calls for M1 and M2); array truncation and timestamp changes were caught in every applicable call (\expDetectApplicableMSix, \expDetectApplicableMEight{} and \expDetectApplicableMThirteen{} calls); string perturbation, identity swaps and number-to-string changes were not caught. The clean traffic has no write calls, so the read-after-write contract was not exercised: all \expDetectApplicableMFourteen{} phantom-write mutants made the tool return an error. No benign mutant was flagged (\expDetectBenignFlagged{} of \expDetectBenignApplicable; upper bound \expDetectBenignWilsonUpper). This measures the circularity noted in \S\ref{sec:limits}: the contracts catch the fault classes they were written for and little else~\cite{jahangirova2016oracle}.

\section{Related work and novelty boundary}
\label{sec:related}

\paragraph{Silent failures and agent benchmarks.} MCP fault studies classify silent faults from issue threads but do not reproduce or repair them~\cite{owotogbe2026mcpfaults}. The robustness studies in \S\ref{sec:why} evaluate how the agent responds to bad tool output~\cite{singh2026scapegoats,zhu2026toolmaze,yang2026overreliance}, not how the tool gets fixed, and $\tau$-bench's tools are deterministic functions over JSON databases~\cite{yao2024taubench}.

\paragraph{Runtime monitors.} Outcome Monitors check results and give the agent recovery affordances, explicitly without repairing the tool~\cite{panthi2026outcomemonitors}; verimcp re-derives outcomes after git, file and CI calls~\cite{verimcp}; a tool wrapper combining postcondition verification, verify-before-retry and idempotency keys reduced duplicate actions in simulation~\cite{mansoor2026verifiedtoolcalls}. Action-side enforcement such as AgentSpec checks planned actions rather than results~\cite{agentspec}. \fiks{}'s receipt step belongs to this line and is not new on its own.

\paragraph{Specification, contract and data validation.} Consumer-driven contracts need the provider to run consumer pacts~\cite{pact-how-it-works}; schema-derived fuzzing finds schema violations~\cite{hatfielddodds2022schemathesis}. Large-scale studies count breaking changes in library APIs~\cite{xavier2017apibreak,kong2025npm}. Data validation systems enforce similar presence, range and distribution checks on batches~\cite{tfdv-2019}, and invariant inference goes back to Daikon~\cite{daikon}. Record/replay tools turn captured traffic into regression tests whose oracle is the old response~\cite{keploy}; that oracle encodes the bug when the recording is made after the drift.

\paragraph{Reproduction and repair.} Issue-to-test generation is hard and its validity is judged by fail-to-pass execution~\cite{libro,mundler2024swtbench,otter}. In a self-healing agent harness 55\% of gate-rejected instruction changes improved their trigger while regressing a protected case~\cite{tayebati2026selfhealingharness}. Repair systems start from issues~\cite{swe-agent,agentless}, compile errors after a dependency bump~\cite{reyes2025byam}, or an upstream breaking change with no localizing failing test~\cite{yang2026deprepair}. Structured upstream evidence helps dependency repair while raw evidence hurts~\cite{yang2026deprepair}; \fiks{} gives the agent a failing test built from the trace, although the pilot prompt also included the raw upstream responses (\S\ref{sec:design}).

\paragraph{Production-driven and commercial loops.} ClearView patched deployed software from learned invariants~\cite{perkins2009clearview}; Itzal validated production-driven patches on traffic~\cite{durieux2016itzal}; SapFix shipped detect--test--repair with human approval~\cite{marginean2019sapfix-paper}. In 2026, observability and alerting products open fix pull requests from errors, incidents or LLM scans and iterate CI after opening~\cite{sentry-seer-issue-fix,posthog-anatomy-pr,devin-oncall,langsmith-changelog-2026}, and some measure recurrence after fixes~\cite{cleric-verifying-fixes}. AegisFlow detects silent pipeline drift statistically and deploys validated patches autonomously for pre-approved failure classes~\cite{awan2026aegisflow}. A granted patent claims language-model repair of a detected issue from its error information, with dependent claims adding a pull request accompanied by a software test~\cite{msft-us12711009}.

\paragraph{What is and is not new.} Table~\ref{tab:matrix} compares the closest systems by loop step, from their documentation or papers; each step exists somewhere. In the sources we reviewed (searched up to 2026-10-21; patent databases only partly searched), we found no system that combines: a trigger that is a deterministic contract violation in a \emph{successful} tool result, checked per call against the raw upstream exchange; a committed test that must fail first for the named property; and all gates, including CI on the exact commit, before the pull request opens, with a receipt to the agent while the fix is pending. We claim only that combination; whether it outperforms a composition of existing parts is the question of \S\ref{sec:protocol}.

\section{Planned confirmatory study}
\label{sec:protocol}
The draft protocol (\texttt{paper/prereg/PREREG.md}) becomes binding only when tagged \texttt{prereg-v1}; none of its runs has been performed. It compares \fiks{} with two alternatives on the same monitor, model, budget and sandbox: \textbf{L1}, the same agent and gates with a pre-PR replay of the triggering trace but no visible reproduction test, and \textbf{COMP}, monitor $\rightarrow$ alert $\rightarrow$ coding agent $\rightarrow$ PR $\rightarrow$ CI with source-run replay. Four hypotheses form the confirmatory family (Holm, FWER 0.05): \textbf{H1}, fewer than 2\% of at least 1{,}500 blind-authored catalog entities give rise to any false positive; \textbf{H2}, the trace-derived repro separates correct from incorrect patches better than an agent-written fail-first repro; \textbf{H3/H4}, \fiks{} exposes fewer green-but-incorrect pull requests than L1 and than COMP, with a correct-PR loss no larger than 0.10. The draft's own power analysis states that if the true correct-PR cost is 0.03--0.05 or the true harm gap is 0.05, H3 and H4 are more likely than not to come out ``not established''. Drifts are authored blind to the contracts and applied by a third-party injector; benign evolution, frozen mutation operators, four real silent-failure bugs in public MCP servers and an adversarial-trace suite are exploratory arms.

\section{Threats to validity and limitations}
\label{sec:limits}

\paragraph{Circularity.} The author wrote the drifts, the contracts and the tasks; detection of D1--D5 is therefore close to a construction property. The mutation sweep (\S\ref{sec:exp}) bears this out: recall on silent mutants from operators with no matching contract check was \expDetectRecallOutsideSilent. Mutation-based oracle assessment and real faults are needed to measure what contracts miss~\cite{jahangirova2016oracle,just2014mutants}, and runtime contract vocabularies have known blind spots on out-of-vocabulary faults~\cite{panthi2026outcomemonitors}.
\paragraph{Scale and statistics.} \nTasks{} tasks and \kTrials{} trials cannot support task-level significance; trial-level intervals ignore clustering~\cite{bowyer2025clt}. The false-alarm bounds come from \vOneCalls{} clean bench calls and \expDetectCleanCalls{} catalog calls on one vendor.
\paragraph{Partial or overfitted patches.} A green suite shows the repro and the recorded contracts pass; it does not prove correctness~\cite{swe-doctor,tan2026coharden}. During development, an adversarial verifier showed that two wrong fixes pass the test suite: a D2 fix that returns a constant in-range price, and a D1 fix that clamps prices to the range ceiling. The pilot measured no held-out oracle; in the ablation (\S\ref{sec:exp}) one \textsc{alert} patch passed the reproduction test, which checks only the count, but broke prices on live v2 because it also applied a unit conversion seen in the all-drift trace; a reproduction of one property does not guard the others.
\paragraph{Prompt hints.} The pilot repair prompt (\S\ref{sec:design}) named the failure class, included the contract and the raw upstream responses, and its general notes point toward the D1, D3 and D4 fixes; the pilot fixes are small, and one-attempt success on these drifts may not carry over to repairs without such context. In the ablation, without these hints the live check passed in \expLiveNohint{} runs against \expLiveFiks{} with them (sign test $p=\expSignFiksVsNohintP$; \S\ref{sec:exp}); the drifts are small and the evidence is weak.
\paragraph{Security.} The repair agent reads attacker-controllable vendor bytes and its code runs in tests. Restricting terminal access does not stop injected agents from writing malicious source~\cite{liu2025aishelljack}, test-passing patches can hide vulnerabilities~\cite{chen2025swexploit}, and injection through tool output is measurable~\cite{debenedetti2024agentdojo,bouras2026capscope}. In the pilot the agent ran without an OS or network sandbox. The ablation and injection runs (\S\ref{sec:exp}) ran the agent's shell commands and all gates in a container with no network (the agent's file tools ran on the host, confined to the checkout), but two runs of one injection template do not measure resistance to prompt injection; the full injection suite is part of the protocol.
\paragraph{Legitimate evolution.} A fixed contract cannot tell a vendor fault from an intended change; the pilot always proposed a code fix. A contract-update outcome is designed but unevaluated.
\paragraph{Pilot build differences.} \nFTwoRuns{} of \nDrifts{} F gates ran twice rather than three times; all \nDrifts{} repairs and the receipt-v1 runs used uncommitted code; and every repair was triggered by a scripted call, not by agent traffic.
\paragraph{External validity.} One mock vendor, one server, one model family (Claude) for both bench and repair, and seeded rather than organic drift. Merged pull requests were merged by an AI assistant at the owner's request without line-by-line review, so they say nothing about maintainer acceptance.

\section{Conclusion}
\fiks{} shows that a silent tool failure caught by the proxy on a call against a drifted vendor can be turned, within minutes, into a named-property failing test and a gate-passing pull request against the tool. The pilot shows feasibility on seeded drifts, and the ablation shows that gates which do not replay the triggering call can pass patches that leave the violation in place; it does not show that the loop beats a composition of existing monitors and coding agents, that its contracts generalize beyond the drifts they were written for, or that its pull requests would be accepted. The draft protocol is designed to test the first two, and maintainer acceptance needs a separate study.

\paragraph{Repair prompt.} The template, from \texttt{packages/repair/src/prompt.ts} at \texttt{\fiksSha} (placeholders in angle brackets; the optional previous-failure section is omitted):
\begin{lstlisting}
You are fixing a bug in shop-mcp, an MCP server that wraps a vendor HTTP API. The vendor changed its behavior without changing its published spec, and shop-mcp now returns wrong data to agents without any error.

## What broke (captured from real traffic)
Tool call: <tool>(<args>)

- <propertyId>: <message>

<METHOD URL -> status, vendor-api-version header, first 800 characters of the body>
<read-back probe, if any>

<first failure message, up to 1,200 characters>

<contract JSON>

## Useful files
- src/tools/*.ts: one file per tool. src/vendor.ts: the HTTP client.
- vendor/openapi.json: the vendor's published spec (it did not change).
- <path of the v1 recording of the same call, or test/fixtures/v1/*.json>: recordings against the previous vendor version (2026-01-01), which shop-mcp still has to support.
- Responses carry a vendor-api-version header (2026-01-01 before the change, 2026-10-01 after).

## Rules
- Change only files under src/. Do not edit tests, fixtures, traces, vendored files, CI, package.json or the lockfile.
- Fix the root cause so the tool returns correct data. Do not return an error instead of data, do not invent or cache values, and do not hide the problem.
- Keep the old vendor version working: the v1 fixtures must keep producing exactly the same output.
