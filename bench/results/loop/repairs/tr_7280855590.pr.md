## Fix
The 2026-10-01 vendor returns 200 with an order id for `POST /orders`, but `GET /orders/o-5002` then returns 404, so the order was never saved. Before the change, the same call saved the order. I think this is because `create_order` never sent the `Idempotency-Key` header. The published spec marks it "Recommended" but optional, and my guess is that the new vendor only saves orders that carry it. That's an inference from the spec and the recordings, not something the vendor documents, so the live re-record is what will confirm it. The fix sends a fresh `randomUUID()` as `Idempotency-Key` on every order. Each call still places one new order, and the header is valid for the 2026-01-01 version too. `pnpm typecheck` and `pnpm lint` pass. `pnpm test` has two expected failures: the repro test and `test/fixtures/v1/order-create.json`, both with UNMATCHED_REQUEST because neither recording includes the new header. All other tests pass, and both recordings need re-recording. Separately, the new version now sends `created_at` as epoch milliseconds, and `get_order` turns that into 1970-01-01. The contract doesn't check that field, so I left it out of this change, but it's still wrong data being returned.
